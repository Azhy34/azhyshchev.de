KI-Agent auf Google Cloud Run: Warum Concurrency=80 im Betrieb crasht

Direkte Antwort: Bei Google Cloud Run (Firebase Functions 2. Generation) setzt 1 vCPU im Hintergrund automatisch concurrency=80 pro Container. Bei einem zustandsbehafteten KI-Agenten (Google ADK oder LangGraph) mit 512 MB oder 1 GB RAM führen 80 parallele Sitzungen sofort zu Out-Of-Memory-Abstürzen, abgebrochenen Kundenchats und Kaltstart-Verzögerungen.

Hier zeige ich die konkreten Risiken für den Geschäftsbetrieb und die zweistufige Architektur (concurrency=15 über HTTP + Cloud Pub/Sub mit concurrency=5), die ich in Frankfurt (europe-west3) produktiv einsetze.

01 · Geschäftsrisiko

Welche Einschränkungen der Standardwert concurrency=80 für Unternehmen verursacht

Im lokalen Test fällt das Standardlimit nie auf. Sobald jedoch bezahlte Kampagnen laufen oder mehrere Kunden gleichzeitig den KI-Berater öffnen, trifft der verdeckte Standardwert direkt auf Umsatz und Zuverlässigkeit:

  • Verlorene Werbeklicks bei Lastspitzen: Öffnen 20 bis 80 Interessenten gleichzeitig den Shop-Chat nach einer Google-Ads-Kampagne, stürzt der überladene 1-GB-Container mit einem OOM-Fehler ab und bricht alle aktiven Gespräche ab.
  • Fehlerhafte Prozesse nach dem Kauf: Warten Zahlungs-Webhooks (z. B. Stripe) synchron auf langsame KI- oder E-Mail-Aufrufe, entstehen bei Lastspitzen 429 Too Many Requests-Fehler. Bestellbestätigungen und Support-Tickets bleiben liegen.
  • Unkalkulierbare Cloud-Kosten: Wer max_instances einfach entfernt, um Abstürze zu vermeiden, öffnet Bot-Angriffen und Retry-Schleifen das Cloud- und API-Budget ohne Obergrenze.

Architektur-Grundsatz für KI im Betrieb

Standardwerte der Cloud sind für zustandslose JSON-APIs optimiert, nicht für KI-Agenten. Klare Concurrency-Grenzen und eine Pub/Sub-Warteschlange machen Ausfallsicherheit und Cloud-Kosten planbar.

02 · Kapazitätsrechnung

Warum concurrency=15 rund 150 bis 200 Live-Nutzer pro Container trägt

Das Limit von 80 auf 15 zu senken bedeutet nicht, dass nur 15 Menschen gleichzeitig auf der Website sein können. Entscheidend ist der Unterschied zwischen geöffnetem Chatfenster und aktiver Server-Anfrage:

  • Während ein Kunde liest oder eine Frage eintippt, belegt er 0 Slots auf dem Server.
  • Ein Slot wird erst für die 3 bis 5 Sekunden der aktiven LLM-Verarbeitung nach dem Klick auf Senden belegt und sofort danach wieder freigegeben.
  • 15 gleichzeitige Senden-Klicks im selben 4-Sekunden-Fenster entsprechen im realen E-Commerce-Verkehr etwa 150 bis 200 aktiv chattenden Besuchern.
  • In Kombination mit max_instances=3 verarbeitet das System bis zu 45 parallele KI-Anfragen pro Sekunde ohne OOM-Risiko und ohne Kaltstarts.

03 · Zweistufige Architektur

Aufgabentrennung: Direct HTTP vs. Cloud Pub/Sub Puffer

Nicht jede KI-Aufgabe gehört auf einen direkten HTTP-Endpunkt. Im Produktivbetrieb in europe-west3 trenne ich das Backend sauber nach Nutzererwartung:

Zweistufiges Routing auf Google Cloud Run (2. Generation): Direktes HTTP für den Live-Chat, Eventarc + Cloud Pub/Sub für Hintergrund-Agenten und Webhooks.

Pfad A: Synchroner Live-Chat (1 GB RAM, concurrency=15)

Wartet ein Kunde direkt am Bildschirm (z. B. im RAG-Kundenservice im E-Commerce), geht die Anfrage per direktem HTTP-Aufruf an den warmen Container mit vorgeladenem google-adk.

Pfad B: Asynchroner Hintergrund-Agent (512 MB RAM, Pub/Sub + concurrency=5)

Für Hintergrundaufgaben (Bestell-E-Mails nach Stripe-Zahlung oder KI-Antwortentwürfe in Telegram) speichert der Webhook den Zustand in 0,1 Sekunden in Firestore und antwortet sofort. Eventarc und Cloud Pub/Sub puffern selbst 1.000+ gleichzeitige Events und liefern sie in sicheren 5er-Paketen an den 512-MB-Worker. 

from firebase_functions import https_fn, firestore_fn, options

# Pfad A: Synchroner Live KI-Chat (1 GB RAM, 15 parallele Anfragen)
@https_fn.on_request(
    region="europe-west3",
    memory=options.MemoryOption.GB_1,
    concurrency=15,
    max_instances=3,
    timeout_sec=30,
)
def berater_api(req: https_fn.Request) -> https_fn.Response:
    return handle_live_chat(req)


# Pfad B: Hintergrund-Agent hinter Pub/Sub + Eventarc (512 MB RAM)
@firestore_fn.on_document_created(
    document="telegram_support_outbox/{docId}",
    region="europe-west3",
    memory=options.MemoryOption.MB_512,
    concurrency=5,
    max_instances=3,
    timeout_sec=120,
)
def deliver_support_outbox(event: firestore_fn.Event) -> None:
    process_support_draft(event)
04 · Code-Sicherheit

Thread-Sicherheit in warmen Containern bei concurrency > 1

Cloud Run isoliert den Speicher innerhalb eines Containers nicht zwischen parallelen Anfragen. Wer trace_id oder span_id in einer normalen globalen Variable speichert, vermischt Daten unterschiedlicher Kunden. Drei Regeln sichern die Datenkonsistenz: 

import contextvars
import threading
import requests

# 1. Telemetrie (trace_id, span_id) pro Anfrage sauber isolieren
_log_context: contextvars.ContextVar[dict] = contextvars.ContextVar(
    "_log_context", default={}
)

# 2. Geteilte In-Memory-Caches und Rate-Limits mit Lock absichern
_cache_lock = threading.Lock()
_token_cache = {}

# 3. Globaler HTTP-Connection-Pool spart 50-150 ms pro TLS-Handshake
_http_session = requests.Session()
05 · Häufige Fragen

Häufig gestellte Fragen (FAQ)

Warum stürzt ein KI-Agent auf Google Cloud Run mit Out-Of-Memory ab?
Bei Google Cloud Run und Firebase Functions (2. Generation) wird ab 1 vCPU (typisch bei 512 MB oder 1 GB RAM) standardmäßig concurrency=80 gesetzt. 80 parallele KI-Agent-Sitzungen mit Google ADK oder LangGraph sprengen jedoch 1 GB RAM und führen sofort zum OOM-Absturz.
Wie viele gleichzeitige Nutzer schafft concurrency=15 auf einem 1-GB-Container?
Ein Slot ist nur während der 3 bis 5 Sekunden aktiven Modell-Antwort belegt, nicht während der Kunde liest oder tippt. Mit concurrency=15 bedient ein einziger warmer 1-GB-Container rund 150 bis 200 gleichzeitig aktive Shop-Besucher ohne Kaltstart.
Wann sollte eine KI-Automatisierung Cloud Pub/Sub statt direktem HTTP nutzen?
Direktes HTTP mit concurrency=15 eignet sich für Live-Chats, bei denen Kunden sofort auf Antwort warten. Für Hintergrundprozesse wie Zahlungs-Webhooks, E-Mail-Versand oder KI-Antwortentwürfe puffert Cloud Pub/Sub mit concurrency=5 auch Lastspitzen von über 1.000 Events ohne 429-Fehler.
Worauf muss man im Python-Code achten, wenn concurrency größer als 1 ist?
Cloud Run teilt den Arbeitsspeicher innerhalb einer Instanz zwischen parallelen Anfragen. Request-Daten wie trace_id und span_id gehören in Python ContextVar statt in globale Variablen, geteilte Caches brauchen threading.Lock() und ausgehende API-Calls sollten eine globale requests.Session() nutzen.
