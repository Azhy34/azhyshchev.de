How to Manage Google Ads with an AI Agent: An MCP Server with Business Rules

How do you manage Google Ads with an AI agent without risking the budget? The agent should not write to the Google Ads API directly. It works through an MCP server that holds the business rules: bid limits, negative keyword lists, a check before every session and a traced record of every change. Below is that setup running on my own Etsy shop.

Starting point

Why not the official Google Ads MCP server

This is my own project, built for my Etsy shop MoonBloom, which sells children's wallpapers and runs Google Ads campaigns in DE, AT, ES and FR. The code is private, so I show short fragments only.

My first question was whether I needed to build anything. Google's documentation (developers.google.com, checked 2026-10-13) describes its official Google Ads MCP server as read-only in the current release. It has three tools: list_accessible_customers, search for GAQL queries and get_resource_metadata. In Google's words: "It cannot modify bids, pause campaigns, or create new assets."

Write access therefore means calling the mutate methods of the Google Ads API directly. The API executes what it is sent. It has no object locking, so concurrent edits raise CONCURRENT_MODIFICATION_ERROR. Google itself recommends test accounts, validate_only and Change History for making changes safely.

My conclusion

The business rules have to live in a layer I own: how far a bid may move, which searches are never wanted, how many ads may run. A prompt can ask the agent to respect them. Code can refuse the call when it does not. That is the whole reason this server exists.

Architecture

Architecture: one FastMCP tool call, end to end

I wrote this MCP server in Python with FastMCP from the official MCP SDK (mcp 1.28.1) over stdio. Claude Code is the agent, and the server is registered in the project's .mcp.json. This is what happens between one tool call and Google:

1. Claude Code calls an MCP tool
  ↓ the mcp_tool() decorator in server.py registers it with FastMCP and tags the call with the tool name
2. Input shield
  ↓ writes: build_request() builds a Pydantic model, a failed rule is journaled as REQUEST_REJECTED, Google is never called
3. Preflight gate
  ↓ refusal_for() returns PREFLIGHT_REQUIRED until the session's log check has passed
4. Business logic in tools/*.py
  ↓ campaign, adgroup, rsa, asset, negative, history, observability, eval and preflight tools
5. Google Ads client with a gRPC interceptor
  ↓ core/client.py logs every RPC and retries read methods only
6. Result and telemetry
  ↓ append_audit_log (secrets redacted) → logs/audit.jsonl → Cloud Logging, span → Cloud Trace

Reads get ID validation (IdArguments, digits only). Writes get a full Pydantic model, so a malformed request dies at step 2.

The client retries read methods only: 2 retries, after 1 s and 2 s plus up to 0.5 s of jitter. Writes are never retried automatically, because a repeated mutation could apply twice.

The rest of the stack: google-ads client library 31.0.0, Pydantic 2.13, the OpenTelemetry SDK with a Cloud Trace exporter and gRPC instrumentation, and Google Cloud Logging.

Business rules

Business rules in code, not in the prompt

Each rule below exists because of money or ad quality, and each lives in a file I can read, not in a system prompt the model may weigh against something else.

Rule Where What happens on violation
Preflight gate shield/preflight.py tools/preflight_tools.py PREFLIGHT_REQUIRED, journaled, no Google call. OK opens the gate. ATTENTION keeps it shut until the owner says "continue" and the agent re-runs with acknowledge=True.
CPC ceiling (Maximize Clicks) tools/campaign_tools.py Steps of ±0.05 EUR only, within 0.10-3.00 EUR, TARGET_SPEND campaigns only. Out of range or uncapped: refused, nothing sent.

Ad group bid shield/models_adgroup.py Allowed range 0.05-3.00 EUR, MANUAL_CPC campaigns only.

The CPC ceiling: a bid the agent can only nudge

Under Maximize Clicks the campaign CPC ceiling is the bid lever that counts, because that strategy ignores ad group bids. So it is the one number that decides what a click may cost. The agent may move it by 0.05 EUR per call and never outside 0.10-3.00 EUR, which caps how much damage one wrong call can do to the cost per click. An uncapped campaign has no known starting point, so the tool refuses to guess one.

tools/campaign_tools.py, the CPC ceiling step
if c.bidding_strategy_type.name != "TARGET_SPEND":
    raise ValueError(f"Campaign '{c.name}' uses {c.bidding_strategy_type.name}, not TARGET_SPEND (Maximize Clicks); it has no CPC ceiling to step.")

curr_micros = c.target_spend.cpc_bid_ceiling_micros
if not curr_micros:
    raise ValueError(f"Campaign '{c.name}' has no CPC ceiling set (uncapped); refusing to guess a starting value.")

step_micros = 50_000 if req.direction == "+0.05" else -50_000
new_micros = curr_micros + step_micros
if not CEILING_MIN_MICROS <= new_micros <= CEILING_MAX_MICROS:
    raise ValueError(f"New ceiling {new_micros / 1e6:.2f} EUR is outside the 0.10-3.00 EUR safeguard.")

The budget: a rounding bug that would look like a Google error

Budgets reach the API in micros. In floating point int(4.10 * 1_000_000) is 4099999, and the API rejects it because it is not a multiple of 0.01 EUR. The helper rounds to whole cents first, so a correct budget never fails in a way the agent would have to interpret. The daily budget itself stays within 1.00-100.00 EUR, so a slipped decimal cannot turn a small daily spend into a large one.

core/client.py, the budget in whole cents
def eur_to_micros(amount_eur: float) -> int:
    """
    Converts EUR to micros rounded to whole cents.
    int(4.10 * 1_000_000) == 4099999, which the API rejects as not a multiple of 0.01 EUR.
    """
    return int(round(amount_eur * 100)) * 10_000

The gate: nothing runs until the log check has passed

The preflight gate is a few lines because the rule is simple: until the session's log check has passed, every non-exempt tool returns the refusal text. The agent cannot argue its way past it, because the refusal happens in code before any tool body runs.

shield/preflight.py, the gate
def refusal_for(function: str) -> Optional[str]:
    """The refusal text when `function` must not run yet, else None."""
    if not required() or is_open() or function in PREFLIGHT_EXEMPT:
        return None
    return REFUSAL

Ad quality and the negative lists

The golden RSA rules protect ad quality: every live ad is complete, starts with the keyword-insertion headline, carries the shop's coupon and stays within the character limits. Creating the new ad and pausing the oldest in one mutate request means an ad group is never left half changed. The negative shields protect the budget the other way round: they keep spend away from searches I never want to pay for, in each language I advertise in.

Observability

Tracing and post-run analysis: closing the loop

Rules in code stop bad calls. They do not tell me whether the agent behaved well over a whole session, or whether someone changed the account behind its back. So I treat one agent run as one turn of a loop. The evals are not a dashboard I might remember to open: their result is the input that decides whether the next run may start.

Trace

Every tool call is a trace

I use an OpenTelemetry TracerProvider with a Cloud Trace exporter (shield/cloud_sink.py). Each tool call produces one span named tools/call plus the tool name, with the attribute gen_ai.tool.name.

gRPC instrumentation adds a child span for every Google Ads RPC inside it, filtered to Google Ads calls only. The agent can open a trace itself with get_cloud_trace, so a slow call can be followed down to the RPC that took the time.

Logs

Structured logs, correlated with traces

Each call writes one JSON line: timestamp, tool, action_type (READ or MUTATION), args, success, error_code, latency_ms, sla_status, a google_ads_api block (calls, ms, failed, retried, methods), request ids, trace id and span id, session_id and operator. Secrets are redacted before writing.

The line goes to logs/audit.jsonl and is mirrored to Cloud Logging. Severity is NOTICE for a successful change, WARNING for a shield refusal and ERROR for a Google-side failure. The trace id sits in the log line, so I can jump from a log entry to its span. The agent reads its own logs with get_cloud_logs.

After the run

After the run: tool health

analyze_tool_health flags a tool as slow when its p95 is above 2500 ms with at least 3 samples. It flags an error spike when there are at least 3 errors, at least 2x the previous window and an error rate of at least 10 percent. Every call over 2500 ms is marked DEGRADED.

After the run

After the run: a deterministic process eval

evaluate_agent_process is a guardrail eval over the journal with no LLM judge, so the same journal always gives the same verdict. It checks four rules:

  • READ_FIRST: the session must read get_change_history before its first change. Otherwise the agent acts on a picture of the account that a person may already have changed.
  • ONE_LEVER: one kind of change per test batch, where changes within 10 minutes form one batch. If a budget and a CPC ceiling move together, I cannot tell which one moved the result.
  • AUTO_FIX_ALONE: auto_fix_collisions_and_dupes pauses keywords without a dry run, so it must never run together with other changes. Run alone, its effect is easy to attribute in the journal.
  • VERIFY_AFTER: verify_changes_logged must run between 15 minutes and 24 hours after the last change. Google's change history lags about 15 minutes, so an earlier check would see nothing.
Around the agent

Changes made around the agent

The agent is not the only one who touches the account. verify_changes_logged reconciles Google's change_event history with the journal's MUTATION rows. A change with no matching MCP call is reported as OUTSIDE_CHANGES: a script, another agent or a person in the UI.

Before the next run

Before the next run: the preflight gate

preflight_log_check runs three checks, TOOL_HEALTH, OUTSIDE_CHANGES and AGENT_PROCESS, over the last 7 days or since the last accepted checkpoint (max 30).

OK opens the gate. ATTENTION keeps every ad tool shut until I have reviewed the findings and say "continue", after which the agent re-runs the check with acknowledge=True. Between 05.10 and 12.10.2026 the gate refused tools three times with PREFLIGHT_REQUIRED, and Google was not called.

Real example

The checker needed checking too (2026-10-05)

On 2026-10-05 two of the three preflight checks read the cloud journal, which started on 05.10, and the third read the local journal, which started on 01.10. As a result AGENT_PROCESS missed five violations. The fix: all three checks now choose the journal source the same way.

Incidents

Incidents the guardrails caught

Most rules in the table above started as a mistake. Each entry names the date, what happened and the rule it produced.

  1. 04.08.2026. A field-mask helper silently dropped a field set to False, so Google accepted an update that changed nothing. I caught it on a manual read-back and sent the update again with an explicit mask. Rule: every update sends an explicit field mask.
  2. 01.10.2026. The RSA deploy paused every ad when 2 or more existed and could drop the first headline. Rule: headline 1 must be the DKI headline, at most 3 RSAs stay enabled, and the oldest is paused in the same request.
  3. 01.10.2026. The bid tool changed ad group bids, which Maximize Clicks ignores. Rule: the tool now steps the campaign CPC ceiling instead.
  4. 05.10.2026. A ceiling change with a malformed direction was rejected by the Pydantic shield as REQUEST_REJECTED. Google was never called. Rule: the shield, not the prompt, decides what a valid request is.
  5. 05.10.2026. A non-numeric campaign ID reached a GAQL query and raised BAD_NUMBER. Rule: an ID validator (digits only) now runs before every read.
  6. 05.10.2026. The journal-source mismatch in the preflight, described above. Rule: all three checks choose the journal source the same way.
  7. 05.10 to 12.10.2026. Three PREFLIGHT_REQUIRED refusals: the gate stopped tools until the log check had passed. Rule: the gate itself, working as designed.
  8. 13.10.2026. The keyword tool rejected a request with 25 keywords (limit 20) and an unsupported country code before calling Google. Rule: read tools validate their input too.

Results on the live account

  • The spend was about 8.92 EUR per day across DE, AT, ES and FR (18.08-17.09.2026).

FAQ

Questions about building a Google Ads MCP server

What is a Google Ads MCP server?
It is a program that exposes Google Ads operations as tools an AI agent can call over the Model Context Protocol. Google ships an official one that only reads. Mine is a custom MCP server in Python with 36 tools, 24 to read and 12 to change an account, and it holds my business rules, so an agent such as Claude Code cannot send arbitrary API calls.
Why not use Google's official Google Ads MCP server?
Google's documentation describes it as read-only: it lists accounts, runs GAQL queries and returns resource metadata. It cannot modify bids, pause campaigns or create assets. Writing means calling the Google Ads API mutate methods directly, and the API executes what it is sent. So the rules about how far a bid may move or how many ads may run have to live in a layer I own.
How do you stop an AI agent from overspending in Google Ads?
I put the limits in code instead of the prompt. A campaign CPC ceiling moves only in steps of 0.05 EUR and must stay within 0.10 to 3.00 EUR, the daily budget within 1.00 to 100.00 EUR, and a request outside the range is refused before Google is called. A preflight gate also blocks every ad tool until the log check has passed.
How do you trace what an AI agent did?
Every tool call creates an OpenTelemetry span named tools/call plus the tool name, exported to Cloud Trace, with a child span for each Google Ads RPC. The same call writes one structured JSON log line with the trace id, mirrored to Cloud Logging, and secrets are redacted. After the run, analyze_tool_health and evaluate_agent_process read that journal.
How do you build an MCP server in Python with FastMCP?
I use FastMCP from the official MCP SDK over stdio. A small decorator, mcp_tool(), registers each function as a tool and tags the call with its name. Pydantic models validate every write before any business logic runs, and Claude Code finds the server through the project's .mcp.json. The hard part is not the protocol but the rules behind each tool.
Can Claude Code manage Google Ads?
It can with a server behind it. In my setup Claude Code reads campaigns, search terms and change history, then changes budgets, CPC ceilings, negative keywords and ads through the 12 write tools. In my setup it has no direct API access, only the server. Every call passes the Pydantic rules and the preflight gate and lands in a traced journal. 237 calls were logged from 01.10 to 13.10.2026.
